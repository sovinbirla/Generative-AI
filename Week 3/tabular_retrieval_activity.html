1

The Limits of Standard RAG

Why the techniques from your Gen AI class break on tabular data

You already know how standard Retrieval-Augmented Generation (RAG) works: chunk a corpus of documents, embed them, and at query time retrieve the most similar chunks to feed to an LLM. This works beautifully for PDFs, articles, and web pages — natural language that carries meaning chunk-by-chunk.

But what happens when the source of truth is a relational database or a set of CSVs?

⚠️
The Core Problem

Standard RAG treats every chunk as a small document. A row from a patient table is not a document. Isolated, it is nearly uninterpretable — and embedding it produces garbage retrieval.

What a "document chunk" usually looks like

A clean paragraph from a cardiology guideline:

"Patients with heart failure and reduced ejection fraction (HFrEF) should be initiated on ACE inhibitors unless contraindicated. The target dose should be achieved gradually over 2–4 weeks to reduce the risk of hypotension..."

This chunk carries its own meaning. You can embed it, retrieve it, and hand it to an LLM — and the LLM can answer questions from it directly.

What a "table chunk" looks like

A row from a hospital patient table, naively serialized:

patient_idadmit_datedrg_codeprimary_icdlos_daysdisch_disppayer_cd
100472024-11-03291E11.9401ME
100482024-11-04470M16.11206BC

Key Insight

Tables have structure — rows relate to columns, columns have types and semantic roles, and values only make sense with their headers. Any retrieval strategy that ignores structure will fail. The Pneuma paper's central claim is that the retrieval target should be metadata and schema, not raw rows.

2

What Is Tabular Data Retrieval?

Reframing the problem — from rows to datasets

Before we can answer a natural language question using data in a database, we need to find the right data. This is a two-level problem that is often conflated.

Level 1 — Catalog Discovery

"Which dataset or table contains what I need?"

Example: "I need a table with diagnosis codes and length of stay." → Find encounters and diagnoses tables.

Level 2 — Content Retrieval

"Which specific rows or values answer my question?"

Example: "Show patients admitted in Q4 2024 with DRG 291." → Execute SQL against the right table.

Standard RAG conflates these. It embeds content and retrieves at the value level. But for tabular data, you almost always need to solve Level 1 first — get to the right table — before Level 2 even makes sense.

The Pneuma Framing

The Pneuma paper frames retrieval this way: the retrieval target is a catalog card — a structured description of a dataset that includes its schema, narrated purpose, column descriptions, and sample values. The LLM then decides which catalog card best matches the user's intent.

📖
Think of it like a library catalog

You don't search a library by reading every page of every book. You search the catalog (title, abstract, subject tags). Pneuma builds an analogous "catalog" for datasets, making each table discoverable by its meaning — not its raw values.

Questions about which dataset or what the data was built for require catalog-level retrieval. Questions about specific values, rows, or computations require content retrieval. Pneuma focuses primarily on the first — because without the right table, the second is impossible.

3

Content Questions vs. Context Questions

Same vector store — very different retrieval quality

Even within catalog discovery, Pneuma draws a crucial distinction between two types of natural language questions:

Content Question

Answerable by inspecting column names and data values.

  • "Which dataset has diagnosis codes?"
  • "Find a table with patient age and BMI"
  • "Which table contains medication names?"

A schema embedding will surface this correctly.

Context Question

Answerable only from documentation, metadata, or stated purpose.

  • "Which dataset was built for Joint Commission reporting?"
  • "Find data collected under HIPAA waiver #2021-04"
  • "Which table supports the readmission reduction program?"

No column name or value will reveal this — you need catalog metadata.

A naive RAG system that only embeds schema information will answer content questions reasonably well. But it will completely fail on context questions, because the answer is not in the data itself — it is in the documentation about the data.

⚠️
Hospital Reality Check

In a real hospital data catalog, many critical questions are context questions. "Which extract do we send to CMS for value-based care reporting?" cannot be answered from column names alone. The Pneuma approach enriches catalog cards with documentation text so context questions become answerable.

Schema Narration

Bridging the vocabulary gap between user queries and technical schemas

Even if you know which table to look in, the column names are often cryptic. Consider this raw schema:

diagnoses(
  diagnosis_id  INT,
  patient_id    INT,
  icd10_code    TEXT,
  primary_flag  INT,
  dx_seq_num    INT,
  poa_indicator CHAR(1),
  dx_version    INT
)

A user asks: "Find data about the main reason for each admission." The answer is hidden in primary_flag = 1 — but nothing in the schema text maps "main reason for admission" to primary_flag. The vocabulary gap kills retrieval.

⚠️
Why Embedding Raw Schema Fails

primary_flag INT embeds near other flags and integer columns. It does not embed near "principal diagnosis" or "primary reason for hospitalization" — the terms a clinician would use — because those phrases don't appear anywhere in the raw schema.

Schema Narration — The Pneuma Solution

Schema narration means using an LLM to generate a rich natural language description of each table and its columns, then embedding that description (not the raw DDL). The narrated version bridges the vocabulary gap.

Key Insight: Vocabulary Gap Bridged

After narration, the embedding of this description will cluster near queries like "principal diagnosis," "primary reason for hospitalization," "present on admission," and "ICD-10 billing codes" — all phrases that would never match the raw DDL. Schema narration is a form of retrieval-time enrichment.

What Good Narration Covers

  • Table purpose: What does this table track? Why does it exist?
  • Grain: What does one row represent? (One diagnosis per admission? One medication per patient-day?)
  • Column semantics: What does each column mean in plain English? Include business rules.
  • Code mappings: What do coded values mean? (e.g., poa_indicator = 'Y' = present on admission)
  • Relationships: What foreign keys exist? What table does this join to?
  • Domain aliases: What do clinicians, analysts, and compliance teams call this data?
5

The Semantic Layer

Mapping business vocabulary to technical SQL expressions

Schema narration helps you find the right table. But even after finding the right table, natural language questions often use business concepts that have no direct mapping to a column name. This is where the semantic layer comes in.

A semantic layer is a repository of mappings from business terms to the SQL expressions that implement them. Without it, NL-to-SQL fails on precisely the questions that matter most in practice.

Examples from a Hospital Data Environment

Business TermSQL Implementation
Active medication end_date IS NULL OR end_date >= date('now')
Readmission Second admission within 30 days of a prior discharge to the same facility
CKD Stage 3+ icd10_code LIKE 'N18.3%' OR icd10_code LIKE 'N18.4%' OR icd10_code LIKE 'N18.5%' OR icd10_code = 'N18.6'
Recent lab lab_date >= date('now', '-90 days')
⚠️
Without a Semantic Layer

An LLM asked "find all readmissions this quarter" might write WHERE admit_reason = 'readmission' — which will return zero rows, because no column stores that label. The business rule (30-day window, same facility, same patient) must be made explicit.

The semantic layer is the difference between a catalog agent that finds the right data and one that can also use it correctly. 6

Latent Intent vs. Explicit Query

What the user typed versus what they actually need

Users rarely type their full analytical intent into a search box. They express a surface query that is a compressed, imprecise representation of a deeper goal. A good catalog agent must surface datasets relevant to the real analytical goal — not just the keywords.

Explicit Query

"Find readmission data for cancer patients"

A naive RAG retrieves datasets mentioning "readmission" or "cancer." Done.

Latent Intent

The analyst wants to run a Joint Commission quality improvement analysis on 30-day oncology readmissions.

They also need: admissions, diagnoses, DRG codes, discharge timestamps, oncology-specific ICD codes, and possibly outpatient follow-up records.

The gap between explicit query and latent intent is where standard RAG fails silently — it returns something, but not everything needed. The analyst doesn't know they're missing data until downstream analysis breaks.

🧠
How Pneuma Addresses This

Pneuma proposes that after retrieval, an LLM should explain why each retrieved dataset is relevant and flag whether joins or additional datasets are needed. The agent becomes a partner in uncovering latent intent — not just a keyword matcher.

💡
Key Insight

Resolving latent intent requires the system to model the analytical goal, not just match keywords. Catalog cards enriched with purpose, provenance, and relationships give the LLM the context to make those inferences. This is why metadata-rich catalog cards are more valuable than schema-only indexes.

7

Putting It Together

The complete Data Catalog Discovery Pipeline

Now that you understand each component, here is how Pneuma assembles them into a coherent pipeline. Each step addresses a specific failure mode of naive RAG.

1

Ingest Catalog Cards with Schema Narration

For each table or dataset in the enterprise, generate a rich catalog card: raw schema + narrated description + column-level annotations + semantic layer definitions + provenance (who owns it, what it's for, compliance tags). Embed the narrated card, not the DDL.

Schema Narration Semantic Layer Metadata Enrichment
2

User Submits a Natural Language Question

The user types a question in plain English — possibly content-oriented, context-oriented, or a mix. No query reformulation required from the user.

Content Question Context Question
3

Vector Search Retrieves Top-k Catalog Cards

The user query is embedded and compared against all catalog card embeddings. Top-k most similar cards are retrieved. Because cards include narrated schema AND documentation, both content and context questions surface relevant results.

Dense Retrieval ANN Search
4

LLM Explains Relevance and Flags Joins

The LLM receives the query + top-k cards and produces: (a) a relevance explanation for each card, (b) a flag if a join between datasets is needed, and (c) a ranked recommendation. This is where latent intent gets surfaced — the LLM can reason about what the analyst is really trying to do.

Reranking Latent Intent Join Detection
5

(Optional) Agent Writes Join Plan and Generates SQL

If the user confirms the dataset selection, an agentic layer can inspect the full schemas, resolve foreign keys, apply semantic layer definitions (business terms → SQL), and generate a complete query — including joins. This closes the loop from natural language to executable SQL.

Agentic Loop NL-to-SQL Semantic Layer Resolution
💡
How This Differs from Standard RAG
  • Retrieval target: Catalog cards (metadata + narration) instead of raw content chunks
  • Enrichment: Schema narration and semantic layer definitions embedded at ingest time
  • Output: Dataset recommendations with explanations, not just retrieved text passages
  • Latent intent: Explicit modeling step, not implicit keyword matching
  • Agentic step: Optional deeper inspection, join planning, and SQL generation
