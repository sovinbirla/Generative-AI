What “nearby” means

An embedding is a high-dimensional coordinate. Texts with related meaning often land near one another even if the wording is different. The system therefore ranks document chunks using a distance or similarity metric such as cosine similarity, inner product, or Euclidean distance.

Important: the vector database does not “understand” the document in the human sense and it does not write the final answer. It retrieves candidate context. In RAG, the language model uses that retrieved context to produce the response.
ChunkingControls the unit of retrieval. Too large can mix topics; too small can remove the context needed to interpret a passage.
Embedding modelDefines the geometry of the semantic space. Documents and queries must be encoded compatibly.
Similarity metricDefines what “close” means mathematically. The metric should match the embedding model and index configuration.
Top-kControls how many candidate chunks are returned. More context is not always better because irrelevant chunks can dilute the prompt.

Why ANN methods appear on the slide

If the collection is small, we can compare the query vector with every stored vector. At large scale, that exhaustive scan is expensive, so vector systems often use Approximate Nearest Neighbor (ANN) indexes to reduce the candidate search space.

HNSW

Hierarchical Navigable Small World builds a multi-layer proximity graph. Search jumps through coarse layers and then refines locally. It is popular because it often provides strong latency/recall performance.

graphhigh recallmemory cost

IVF

Inverted File Index partitions vectors into clusters. A query probes only a subset of nearby clusters instead of scanning the full collection. More probes usually improve recall but increase latency.

clusteringcandidate pruningtunable

PQ

Product Quantization compresses high-dimensional vectors into compact codes. This reduces memory and can speed distance estimation, at the cost of approximation error.

compressionmemory efficientlossy
Teaching nuance: HNSW, IVF, and PQ are not mutually exclusive categories. Systems can combine them—for example IVF+PQ, and modern vector engines may also combine graph search with quantization.
30-second classroom explanation

“Imagine every paragraph in our document library as a pin on a giant semantic map. The user question becomes another pin. Retrieval means finding the closest pins. When the map has millions of points, we do not want to measure the distance to every pin, so we build shortcuts—graphs, clusters, or compressed representations—to get to the right neighborhood quickly.”

Original Slide 2 · Nearest neighbor search vs vector databases

The search algorithm and the database are different layers

Once the query is embedded, the mathematical task is simple: find the nearest vectors. The engineering question is how much infrastructure we need around that search.

NumPy / brute forceStore vectors in an array, compute similarity to every row, sort, and take the top-k. Simple, transparent, and exact.
ANN libraryUse libraries such as FAISS or Annoy to build specialized indexes that make nearest-neighbor retrieval faster or more memory-efficient.
Vector databaseAdd durable storage, metadata, filtering, APIs, concurrent access, index lifecycle management, and production operations around vector search.

1. Exact nearest-neighbor search

The most straightforward implementation computes a distance or similarity score between the query and every vector in the archive. For a modest collection, this can be entirely reasonable and is often the cleanest baseline.

Do not teach a hard vector-count threshold. “Thousands or tens of thousands” is a useful intuition, but the practical break-even point depends on dimensionality, hardware, batch size, latency target, and query volume.

Conceptually

scores = X @ q (for normalized vectors / dot-product style search), then select the top-k rows. That is nearest-neighbor retrieval without a database.

2. Search libraries such as FAISS / Annoy

These libraries focus on vector indexing and similarity search. FAISS, for example, includes exhaustive indexes as well as ANN techniques such as inverted files, product quantization, and HNSW.

Useful when: you control the application process, want a fast local index, have limited operational requirements, or are prototyping retrieval before adding a database layer.
3. What a vector database changes
Durability
Persist vectors and associated records instead of treating the index as only an in-process data structure.
Metadata filtering
Combine semantic similarity with constraints such as year, source, department, modality, tenant, or permissions.
Data mutation
Support inserts, deletes, and updates as part of normal application workflows. How indexes are maintained is implementation-specific.
Serving
Expose APIs / SDKs and handle concurrent queries from multiple applications or users.
Scaling
Provide mechanisms for partitioning, replication, resource management, and larger-than-single-process workloads.
Operations
Add access control, monitoring, backups, metrics, logs, and lifecycle management depending on the product.
Key distinction: nearest-neighbor search is a capability; a vector database is a system that exposes and operates that capability along with data-management features.

“NumPy gives us the math. FAISS gives us a specialized search engine. A vector database wraps that search capability in the machinery we expect from a production data service—storage, filters, APIs, updates, scaling, security, and monitoring.”

Original Slide 3 · Vector DB vs NumPy NN (or FAISS)

A vector database is more than an ANN index

Vector DB ≈ vector index/search + metadata store + service API + production operations
Use the “FAISS + Postgres + REST API + DevOps” equation as an analogy, not a literal implementation. Some vector databases use different internal engines, and general-purpose databases with vector extensions can provide overlapping capabilities.

Common misconception: “FAISS versus vector database” is not always an either/or architectural decision. FAISS is a search library and can be embedded inside a larger system. A database/service adds operational and data-management concerns around the search primitive.
30-second classroom explanation

“The vector index is the engine, but the database is the car. The engine makes search fast; the car adds storage, controls, interfaces, monitoring, and everything needed to operate reliably in traffic.”

Class recap

Four ideas students should leave with

1. Embed

Documents and queries are mapped into the same high-dimensional vector space.

2. Retrieve

Nearest-neighbor search ranks chunks by vector similarity or distance.

3. Approximate

ANN indexes such as HNSW, IVF, and PQ trade a little exactness for speed and scale.

4. Operationalize

A vector database wraps search with persistence, metadata, APIs, updates, scaling, security, and observability.

One-line summary: embeddings create the space; nearest-neighbor algorithms search the space; vector databases make that search usable as a production data service.
