Building a Domain-Specific Language Model

Continued pretraining, instruction fine-tuning, classification fine-tuning, and when to use none of them. One airline example from start to finish, plus the math to size a project.

1 · The problem

"Fine-tune it on our documents"

Every company with a large document archive eventually asks the same question. An airline has gigabytes of maintenance manuals, aircraft logbooks, operating procedures, and safety reports. General-purpose LLMs have never seen any of it. The intuitive plan is to take an open model and "fine-tune it on everything".

The intuition is half right. There is a training stage that consumes raw, unlabeled domain text, but it isn't what most people mean by fine-tuning, and on its own it doesn't produce a model that reliably answers questions about the domain. To see why, we need to separate the training stages precisely.

The one-line takeaway: training teaches a model to speak the domain; retrieval tells it what is true today. Most domain projects need both, and retrieval usually comes first.
2 · The training stages

Five ways to change what a model does

Four of these change the model's weights. The fifth (retrieval) changes only what the model sees at question time.

PretrainingTrillions of tokens of general text. Next-token prediction. Done once, by the model provider.
→
Continued pretraining (CPT)Your raw domain text. Same next-token objective. No labels.
→
Supervised fine-tuningLabeled pairs: instructions → responses (IFT), or text → class (CFT).
→
Preference alignmentPreferred vs. rejected answers (DPO, RLHF).
Retrieval-augmented generation (RAG): no trainingSearch your documents at question time and place the relevant passages in the prompt. Works with any of the models above.

What each stage optimizes

The differences are easiest to see in the loss functions. Let x be a sequence of tokens, θ the model's parameters.

# Pretraining and continued pretraining (CPT): every token is a target LCPT(θ) = − Σt log pθ(xt | x<t) over ALL tokens of the raw document # Instruction fine-tuning (IFT): same loss, but only on the response tokens LIFT(θ) = − Σt ∈ response log pθ(xt | x<t) instruction tokens are context, not targets # Classification fine-tuning (CFT): new head W ∈ ℝd×K on the last token's hidden state h LCFT(θ, W) = − log softmax(hlast W)y K classes instead of a 50k+ vocabulary # Preference alignment (DPO): push up the chosen answer yw, push down the rejected yl LDPO(θ) = − log σ( β [ log πθ(yw|x)/πref(yw|x) − log πθ(yl|x)/πref(yl|x) ] )
StageData you needWhat it changesWhat it does not do well
CPTRaw domain text, ideally billions of tokens. No labels.Vocabulary, phrasing, domain fluency. Lowers perplexity on domain text.Doesn't teach the model to answer questions or follow instructions; can erode both.
IFTThousands of (instruction, response) pairs.Task behavior, output format, tone.A weak and risky way to add new facts.
CFTThousands of (text, label) pairs over a fixed label set.One narrow skill, done reliably and cheaply.Can only ever output its classes.
DPO(prompt, chosen, rejected) triples, often from experts.What the model refuses, how it handles uncertainty, whether it cites sources.Adds no knowledge.
RAGThe documents themselves, indexed for search.Which facts the model sees for each question. Current and citable.Only as good as retrieval; can't count or aggregate across thousands of records.

CPT is Ch. 5's training loop pointed at a new corpus.
3 · Same airline, five jobs

What the training data looks like at each stage

All examples below are fictional, but written the way airline documents are. The point is that the same company needs different data for each stage, and only one stage can use the raw documents as they are.

Continued pretraining: raw text, as-is

TASK 32-41-00-200-801
Brake Wear Inspection
(1) Set the parking brake.
(2) Measure the wear-pin extension.
    If the pin is flush with the housing,
    replace the brake assembly ...

LOG 14-MAR  L/H MLG TIRE WORN TO LIMITS,
REPLACED IAW AMM. OPS CK GOOD.

Learns: how manuals and logbooks are written, what "IAW", "MLG", and "OPS CK" mean in context.

Instruction fine-tuning: (instruction, response)

{"instruction": "Summarize this delay report for the
   duty manager in three bullets.",
 "input": "Flt 1234 ORD-SFO delayed 2h10m. APU
   inop, ground power unavailable at gate ...",
 "response": "• 2h10m delay, ORD-SFO\n• Cause: APU
   inoperative, no ground power at gate\n• Action:
   aircraft swap at 14:20"}

Learns: to perform a task in a required format. Usually written by experts, often expanded with synthetic examples.

Classification fine-tuning: (text, label)

("L/H MLG TIRE WORN TO LIMITS, REPLACED",   32)
("APU WILL NOT START, FAULT CODE 0472",      49)
("AFT LAV FAUCET LEAKING",                  38)
("CAPT WINDSHIELD HEAT INOP",               30)

Learns: map a defect write-up to its ATA chapter (32 landing gear, 49 APU, 38 water/waste, 30 ice and rain protection). Logbooks often already contain these labels.

Preference alignment: (prompt, chosen, rejected)

prompt:   "Can I dispatch with the APU inop?"
chosen:   "Possibly, under the MEL. The current
           revision says ... [source: MEL 49-1,
           rev. 12]. Confirm with Maintenance Control."
rejected: "Yes, that's fine."

Learns: cite sources, defer to the right authority, don't sound certain when it isn't.

RAG: no training data at all

question → search index (filtered to
           fleet = 737, revision = current)
         → top passages from MEL 49-1, rev. 12
         → prompt = question + passages
         → answer with citation

Gives: facts that are current, citable, and change the day the document changes. Nothing is stored in the weights.

4 · Why raw documents aren't enough

Five reasons "just CPT on the manuals" falls short

  1. Facts seen once are stored but hard to retrieve from the weights. Allen-Zhu & Li (2023) trained models on synthetic biographies: when each fact appeared in only one phrasing, the model memorized the text but couldn't answer questions about it. When facts appeared in many paraphrases, it could. A manual states each procedure once.
  2. Raw CPT can erode instruction following. Cheng et al. (2023) found that continued pretraining on raw domain text improved domain knowledge but hurt the model's ability to answer prompts. Converting the raw text into reading-comprehension tasks fixed it.
  3. Fine-tuning on new facts encourages hallucination. Gekhman et al. (2024): examples containing facts the model didn't already know are learned slowly, and once learned, they make the model more likely to hallucinate. For injecting knowledge, retrieval beat fine-tuning (Ovadia et al., 2023).
  4. Regulated content changes, and weights can't cite. Procedures, minimum equipment lists, and airworthiness directives are revised on a schedule. Whatever was in the training data is frozen into the weights, without a revision number or a source. In aviation, quoting a superseded procedure is a safety issue.
  5. Much of the corpus is really a database. Logbook entries and work orders are records with dates, tail numbers, and part numbers. "How many tire changes last quarter?" is a query, not something to memorize.
Cautionary tale: BloombergGPT (Wu et al., 2023). A 50B-parameter model trained from scratch on ~363B tokens of financial text plus ~345B general tokens. It beat open models of its time on finance benchmarks, but later evaluations found GPT-4 outperformed it on many finance tasks with no finance-specific training. Training from scratch is rarely the best use of a domain budget.
5 · The math

Sizing a domain-model project on one page

5.1 From bytes to tokens

English text under a BPE tokenizer averages about 4 bytes (≈ 0.75 words) per token. Two warnings:

  • Files are not text. A folder of scanned PDFs, images, and spreadsheets yields far less clean text than its size suggests. Measure after extraction and deduplication.
  • Domain shorthand costs extra tokens. With the GPT-2 tokenizer, the 9-word logbook entry L/H MLG TIRE WORN TO LIMITS, REPLACED IAW AMM takes 19 tokens (TIRE → TI + RE), while the 15-word plain-English version takes 16. That's one reason CPT helps on jargon-heavy text.
tokens ≈ bytes of clean text / 4 # 1 GB of clean text ≈ 250M tokens

5.2 The Chinchilla rule: how much data a model "wants"

Hoffmann et al. (2022) found that for a fixed compute budget, loss is minimized when training tokens scale with parameters, at roughly 20 tokens per parameter.

Dopt ≈ 20 × N # N = 1B → ~20B tokens # N = 3B → ~60B tokens # N = 8B → ~160B tokens # N = 70B → ~1.4T tokens (Chinchilla itself: 70B params, 1.4T tokens)

Modern open models train far past this point (Llama 3 8B saw ~15T tokens, about 1,900 per parameter), because a smaller model that was trained longer is cheaper to serve on every future query. Either way, the consequence for a company is the same: a company corpus is orders of magnitude too small to pretrain from scratch. CPT works precisely because it starts from a model that has already seen trillions of tokens.

5.3 Compute: the 6ND rule

Training a transformer costs about 6 FLOPs per parameter per token: 2 for the forward pass and 4 for the backward pass.

C ≈ 6 × N × D # total training FLOPs GPU-seconds ≈ C / (peak FLOP/s × utilization) # H100, BF16 dense peak ≈ 9.9 × 10¹⁴ FLOP/s; realistic utilization 30–50% # → use ≈ 4 × 10¹⁴ FLOP/s per GPU for estimates

5.4 Worked example (a different corpus from the challenge)

A regional airline has 2 GB of clean text and wants to adapt a 1B-parameter open model.

Tokens: 2 × 10⁹ bytes / 4 = 5 × 10⁸ tokens (500M) From scratch: Chinchilla wants 20 × 1B = 20B tokens → corpus is 40× too small CPT compute: 6 × 10⁹ × 5 × 10⁸ = 3 × 10¹⁸ FLOPs per epoch GPU time: 3 × 10¹⁸ / 4 × 10¹⁴ = 7,500 s ≈ 2 GPU-hours per epoch
The lesson of the arithmetic: CPT compute for a company-sized corpus is cheap: hours to days of GPU time. The expensive parts are getting clean, permitted data, expert-written evaluation sets, and keeping the result current.

5.5 Memory: will it fit?

# Full fine-tuning with Adam, mixed precision ≈ 16 bytes per parameter (+ activations) # 2 (BF16 weights) + 2 (BF16 gradients) + 12 (FP32 master weights + Adam m and v) 1B model → ~16 GB # one GPU 8B model → ~128 GB # several GPUs (sharded, e.g. DeepSpeed ZeRO / FSDP) # Inference (weights only) 8B in BF16 → ~16 GB 8B in 4-bit → ~4–5 GB # fits a laptop GPU; this is what QLoRA trains on

LoRA and QLoRA cut training memory sharply by freezing the base weights. They work well for IFT. For CPT, where the goal is absorbing a lot of new text, Biderman et al. (2024) found LoRA learns noticeably less than full fine-tuning (and forgets less of what the model already knew). Full fine-tuning is the usual choice for CPT.

5.6 Rules of thumb

QuantityRule of thumb
Tokens in English text≈ bytes / 4 ≈ words / 0.75
Compute-optimal data (Chinchilla)≈ 20 tokens per parameter
Training compute≈ 6 × parameters × tokens FLOPs
Realistic H100 throughput≈ 4 × 10¹⁴ FLOP/s (≈ 40% of BF16 peak)

8 · The recipe

Building a domain model, in order

Each step has a gate: if the evaluation shows the gap is closed, stop there.

  1. Define the tasks and build the evaluation first. A golden set of a few hundred questions written by domain experts, with correct answers and source citations. Measure baselines: a strong general model with no context; the same model with RAG; a small open model with RAG.gate
  2. Build strong retrieval. Combine keyword search (BM25) with dense embeddings, since exact strings like part numbers and ATA codes are where dense search is weakest. Filter by metadata such as fleet type and revision. Send record-level questions to NL-to-SQL. Fine-tuning the embedding model and reranker is often the best value here.gate
  3. Prepare the corpus. Extract and OCR, deduplicate, remove personal data, keep revision dates, and confirm you are allowed to train on each source (licenses on manufacturer manuals, export-controlled technical data).
  4. Make the corpus learnable. Turn raw text into reading-comprehension and Q&A tasks (Cheng et al., 2023), and generate diverse paraphrases about each entity (synthetic continued pretraining, Yang et al., 2024).
  5. Continued pretraining. Full fine-tuning of a 1–8B base model for 1–2 epochs, with general-text replay and a reduced learning rate. Track domain perplexity (should fall) and general benchmarks (should not drop).gate
  6. Instruction and classification fine-tuning. Expert-written and expert-verified synthetic instruction data, mixed with general instructions (LoRA is fine here). Classification heads for narrow routing tasks. RAFT so the model learns to answer from retrieved passages and ignore irrelevant ones.gate
  7. Preference alignment and deployment. DPO on expert preferences (cite sources, defer, say "I don't know"). Quantize for on-premise serving. Re-run the golden set after every change.
When is CPT actually worth it? When a strong model with good retrieval still misreads dense domain language, or a hard constraint (on-premise or air-gapped deployment, latency, cost per query) forces you onto a small model that must do more on its own.
